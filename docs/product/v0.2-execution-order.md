# v0.2 Execution Order

## Current Global Execution Goal

Build the first externally understandable, local-first governed review application while preparing a continuous fundraising demonstration in which a user can import media, obtain a non-authoritative ASR observation, make explicit human-governed corrections, and demonstrate bounded correction reuse on related material.

The immediate v0.2 validation question remains external testability: can a target-adjacent human understand and complete a credible Lead A review workflow? The fundraising demonstration is a delivery target, not a version number. Code completion or a successful demonstration does not establish v0.2 or v0.3 without the evidence required by `versioning.md`.

This document records execution order rather than accepting future contracts. Version semantics remain owned by `versioning.md`; accepted durable boundaries remain owned by Material Decisions.

## Delivery Profiles

Assisted-pilot readiness and fundraising-demo readiness are different delivery profiles. Neither is a separate product version, and neither by itself establishes a version.

### Assisted Pilot

```yaml
purpose: >
  Test whether a real target-adjacent user can understand and complete the
  governed review workflow.
external_SRT_import: allowed
built_in_ASR_required: false
operator_assistance: allowed
primary_version_relationship: v0.2_external_testability
```

An assisted pilot may use an externally produced SRT. This allowance supports a bounded validation session and does not declare external SRT to be the permanent preferred onboarding flow.

### Fundraising Demonstration

```yaml
purpose: >
  Demonstrate a coherent product experience and commercial thesis without
  requiring the observer to mentally assemble several unrelated tools.
media_import: required
built_in_ASR: required
external_SRT_import: retained
governed_review: required
human_confirmed_manual_correction: required
bounded_correction_reuse_demonstration: required
self_service_or_production_readiness: not_implied
```

Built-in ASR is an onboarding capability and a producer of an immutable, non-authoritative `TranscriptObservation`. ASR output never becomes canonical transcript authority. Only explicit human decisions can authorize canonical reviewed output.

The ASR runtime, model, backend, and distribution mechanism remain unresolved. External SRT import remains supported alongside the fundraising-demo media-to-review path.

## Ordered Gates

Bounded engineering overlap is allowed where dependencies permit, but it must not bypass or silently resolve these semantic gates.

### Gate 1 — Native Desktop Review Foundation

```text
SRT + session terms
→ declared authority
→ ApplicationReviewSession
→ review queue
→ explicit existing decisions
→ current projection
→ authority-complete export
```

Implement the MD-016 native desktop foundation as a bounded review surface. This gate does not imply Manual Replacement text, ASR, persistence, Experience, or media playback.

### Gate 2 — Governed Manual Replacement On An Existing ReviewCase

Planned objective only:

```text
existing ReviewCase
→ explicit human replacement text
→ append-only authority
→ deterministic reviewed output
→ replay and export
```

This gate requires a separate owner semantic decision and work package. Manual Replacement payload semantics are not accepted here. Human-raised review cases remain separate.

### Gate 3 — Minimal Governed Correction-Memory Semantics

Planned objective only:

```text
human-confirmed correction
→ bounded candidate
→ explicit acceptance or rejection
→ governed reusable record
```

This gate does not preselect an ontology, scope hierarchy, precedence rule, conflict rule, lifecycle, or durable format. Correction Memory semantics remain unresolved.

### Gate 4 — Product-Session Durability Mechanism And Integration

A product session must eventually support credible restart and resume behavior. This gate does not select SQLite, JSON, an append log, or another mechanism. Existing persistence evidence and accepted durability requirements do not silently select product integration.

### Gate 5 — Fixed Local ASR Observation Adapter

```text
authorized media
→ bounded local ASR job
→ immutable non-authoritative TranscriptObservation
```

This gate records the product role only. It does not select `whisper.cpp`, another runtime, a model, a backend, or a distribution policy.

### Gate 6 — Media / ASR Desktop Integration

Planned user flow:

```text
media selection
→ ASR progress / cancellation / failure handling
→ validated transcript observation
→ governed review session
```

Playback is not necessarily part of this gate. Media playback architecture remains unresolved.

### Gate 7 — Deterministic Related-Material Reuse Demonstration

Target signal:

```text
a human-confirmed correction from Material A
→ governed reusable input
→ a useful candidate on related Material B
→ at least one repeated correction avoided
→ zero unauthorized canonical changes
```

This signal is closely related to the v0.3 establishment question. A scripted or owner-operated fundraising demonstration does not by itself establish v0.3, prove general reuse value, or prove time savings.

### Gate 8 — Assisted External Pilot And Evidence Capture

Run an assisted external pilot to gather evidence about target-user comprehension and completion of the governed review workflow. The evidence and establishment rules remain owned by `versioning.md`.

### Gate 9 — Fundraising-Demo Hardening

Prepare coherent presentation, bounded failure handling, a reproducible demo setup, and truthful product claims. Demo hardening does not imply self-service operation, fundraising readiness achieved, or production readiness.
